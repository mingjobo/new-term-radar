# 以 new-term-radar 为主的统一研究平台架构设计

日期：2026-10-21
状态：待用户审阅
功能范围：[免费关键词研究工作台 V1 需求](2026-10-21-free-radar-sitemap-v1-requirements.md)

## 目标和已确认的边界

最终只保留 `mingjobo/new-term-radar` 这一个开发、部署和自动运行的项目。原 `new-term-radar` 的发现规则、CLI 和上游兼容性是主干；我们已做出的 Neon、网页能力以及旧 `keyword-detective` 中有价值的资产融入主干，不再把 `keyword-detective` 和 `radar_platform` 当成两个长期并行运行的应用。

第一版完成已确认的“总览／关键词看板／设置”“新词／竞品”工作台，以及 GitHub/HF 和每日竞品 Sitemap 的免费自动链路。Google Trends 的**自动采集和历史数据展示都属于第二版**；第一版不加第三个页签、不运行旧浏览器采集，也不从旧 Trends 表生成今日新词。旧表和本地旧目录保留，不删除、不搬入公开仓库。第二版在同一项目中移植所需能力，不恢复第二套网站和任务。

## 方案选择

| 方案 | 结果 | 取舍 |
|---|---|---|
| **选用：单主干、分阶段合并** | `radar/` 是唯一 Python 主包；平台设施成为包内模块；旧项目的相关数据/规则按版本迁入 | 一次性迁移现有平台模块并验证打包，但之后只有一套应用和部署边界 |
| 两个应用并排 | `radar/`、`radar_platform/` 和旧项目各有入口 | 短期少搬文件，长期任务、规则和修复容易分叉，不符合“融到一起” |
| 一次搬入旧项目全部代码 | 旧 Trends 浏览器、旧 UI、旧数据访问也立刻进入主包 | 第一版出现未启用的大量代码和运行依赖，阻碍免费云端链路验证 |

## 代码边界

```text
new-term-radar/
├─ radar/                         唯一业务包和命令入口
│  ├─ __main__.py                 既有命令保持可用；新增免费 collect 入口
│  ├─ breakout.py / sources.py    原有 GitHub/HF 名称与发现规则
│  ├─ sitemaps.py                 上游旧命令兼容；共用纯 URL 解析能力
│  ├─ sitemap_urls.py             公开 Sitemap 的安全读取、完整性和 URL 规范化
│  └─ platform/                   Neon、任务、网页和免费采集适配层
├─ api/index.py                   唯一 Vercel 网页入口 → radar.platform.web
├─ schema/platform/              平台增量迁移；旧 Trends 表原样保留
└─ .github/workflows/            独立免费任务；上游付费工作流保持关闭
```

将现有 `radar_platform/` 的有效模块有测试地迁至 `radar/platform/`，改为同一主包的内部设施，不保留两套业务实现或长期导入路径。`pyproject.toml` 必须同时正确打包 `new_term_radar` 及其 `platform` 子包；从源码 `python -m radar`、安装后的 `new-term-radar` 命令和 Vercel 入口都要通过测试。迁移完成后清理旧 `radar_platform/` 路径及引用；旧 CLI 命令为上游兼容保留，但**不在第一版定时任务中运行**。

原项目与新平台的责任划分：

| 现有资产 | 第一版处理 |
|---|---|
| `radar/breakout.py`、`radar/sources.py` 的纯名称、评分/分组规则 | 作为 GitHub/HF 免费采集的领域规则；平台适配层只负责请求、Neon 状态和证据映射。若现有适配器有不同阈值，先用兼容测试确定唯一规则，再消除重复实现 |
| `radar/sitemaps.py` 的 URL 获取与词暴涨输出 | 抽出可共享的 URL 解析/规范化核心；旧命令行为保持兼容。第一版新监测只记录 URL 新增/移出，**不调用**从路径提词的旧输出 |
| `radar/snap.py` 的 gzip 文件、`radar/store.py` 的 SQLite | 仅供未调度的旧 CLI 兼容；第一版自动链路的事实来源只有 Neon，不做双写或从 Actions cache 恢复事实状态 |
| `keyword-detective` 的 85 个词根 | 已迁入 `config/root-keywords.json`，保留来源说明；不把词根本身算成新发现或搜索量证据 |
| `keyword-detective` 的旧 Neon Trends 表与本地数据/浏览器配置 | 第一版不查询、不展示、不执行；保留表和旧目录，第二版再制定只读接入与采集迁移，不复制 `.env`、浏览器 profile 或抓取产物 |
| 现有 Term Signal 模板、原生 JS/CSS 和 Basic Auth | 迁入主包下的 `platform`，按已确认的极简侧栏原型重排，保留 `/terms/{id}` 研究卡与原始出处 |

这是“一个主项目、一个第一版运行链路”的合并，不是说第一版必须把旧项目每行代码复制过来。没有进入第一版运行与展示的旧 Trends 能力明确作为第二版迁入项，避免名义合并、实际上继续维护双系统。

## 运行和数据流

1. 独立的免费 GitHub Actions 工作流调用主程序的 `collect` 子命令；GitHub、HF Models、HF Spaces 每 8 小时，各站 Sitemap 每日一次。上游 `daily/sources` 仍可人工用于原有功能，但工作流不会调用它们，也不会要求付费密钥。
2. 采集适配层复用 `radar/` 的领域规则，通过受预算和外部地址限制的 HTTP 客户端获取数据。GitHub/HF 的完整结果与 Neon 中的前次成功快照比较，保存词条、证据和运行记录；不完整结果不能推进基线。
3. “设置”把竞品名称、主页和可选 Sitemap 地址保存到 Neon；下一次每日任务读取同一配置。首次完整抓取只建 URL 基线。之后只对两次**完整** URL 集合做差，事件类型为“新增页面”或“移出站点地图”，不推断网页真的删除或其正文变化。
4. Vercel 上同一个 WSGI 网站查询 Neon 已保存的结果。左侧只有“总览／关键词看板／设置”；看板顶部只有“新词／竞品”。总览可选北京时间日期；新词只看当天线索；竞品先看站点汇总，再看单站 URL；来源基线和站点输入只在设置。浏览网页不会启动采集。

Neon 仍用现有 `keyword-detective` 项目及 `dev-free-platform` 开发分支；旧 Trends 表保持不变。第一版继续使用既有 `radar_*` 词/证据/任务表，再为竞品站点配置、URL 基线和事件添加版本化表。URL 事件与关键词证据分开存储，不把 URL 路径自动当作关键词。只用一个网站、一个只读 API 连接和一个限权设置连接；采集者写入连接只在定时任务中，迁移者连接只在显式迁移时。部署仍复用现有 Vercel 项目和预览环境，不创建第二个网站。

## 故障、安全与成本边界

- 单个来源或站点失败不会阻断其他站点；失败、空 Sitemap、缺失分片、格式错误、超出 20 文档/20,000 URL 预算时不替换旧快照、不产生误报的“移出”。最近一次尝试与最近成功时间分开展示。
- 添加站点只允许 HTTP(S) 公网地址。保存、抓取和每次重定向都验证主机和解析 IP；实际连接须使用已验证的公网 IP，避免校验后 DNS 重绑定。遵守 robots 和抓取间隔。
- 工作台用单用户 Basic Auth；普通 API 使用只读数据库角色，设置写入另用仅可操作站点配置表的角色，并检查请求来源以防跨站提交。浏览器不接触数据库密钥；外部文本作为文本展示，链接仅允许 HTTP(S)。
- 免费阶段不启用 AIsa、GoAnyAPI、DataForSEO、TrustMRR 或付费模型入口，不要求旧本地浏览器常驻。没有数据时说“未采集”，成功且无变化时才显示 0。

## 迁移和验收顺序

1. **合并包结构而不改变行为。** 在测试保护下把已完成的平台代码归入 `radar/`，统一 CLI、打包和 Vercel 导入；上游测试、现有 GH/HF → Neon → 网页链路必须保持通过。此时不能同时保留两个被调度的采集入口。
2. **验证持续采集。** 对 GitHub/HF 做真实第二次运行及同周期重试，确认运行记录更新、词条不重复，再开启 8 小时免费任务。
3. **接入竞品。** 先完成安全读取、Neon 站点配置和原子差分；用 `aiphotoeditor.com` 建立真实基线，首次事件为 0，用受控样例验证 3 新增、2 移出及故障保留基线。
4. **完成工作台。** 按已确认原型完成日期、新词、竞品和设置；浏览器测试覆盖桌面、窄屏、分页、研究卡、空状态和权限。页面计数与 Neon 查询逐项核对。
5. **预览验收后再考虑正式启用。** 开发 Neon 分支、Vercel 预览及免费工作流分别验收；无跳过的集成/浏览器测试，真实连续运行记录，凭据隔离确认。正式环境迁移和启用另作明确决定。

回退时先关闭免费工作流，再回退 Vercel 部署；新表数据保留供排查，不删除旧 Trends 表、旧项目目录或上游命令。只有第一版链路稳定后，第二版才设计 Google Trends 历史展示与自动采集如何迁入同一 `radar/` 主包。
