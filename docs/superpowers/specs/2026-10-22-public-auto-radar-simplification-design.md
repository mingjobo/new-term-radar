# 单人关键词雷达：公开网页与自动采集精简设计

日期：2026-10-22

## 目标与已确认边界

以现有 `new-term-radar` 为主项目，交付一个能持续更新、一个人方便查看的关键词研究网站。第一阶段免费来源为 GitHub、Hugging Face Models、Hugging Face Spaces，以及竞品 Sitemap；数据存到现有 Neon 项目，网页部署到现有 Vercel 项目。用户无需点击“研究”或“采集”。

网站不设登录账号、密码、口令、会话或用户表。任何知道网址的人都能看数据，也能在“设置”里添加、修改、暂停和恢复竞品；用户已明确接受这一公开编辑边界。浏览器不能直接连接 Neon，也不能拿到数据库密钥。Google Trends 历史数据、付费 API、页面内容变化比对和独立账号系统不属于第一阶段。

## 选择的实现方式

继续使用现有 Python 网站、原生 HTML/CSS/JS、Neon 表和采集器，不拆成新的前后端项目，不更换数据库，不引入新框架。移除网站的 Basic Auth 与对应环境变量；保留现有设置接口、网址安全检查、Sitemap 完整性检查和源数据去重规则。现有 reader、site-admin、writer、migrator 数据库技术权限继续用于服务端部署，不新增第五套权限；它们不是网站登录账号，也不要求用户日常管理。本次不重写已通过验证的采集核心。

当前已建但未使用的 `radar_relations`、`radar_checks`、`radar_reports` 表不对外提供功能，也不做删除迁移；删除生产数据不是“精简”的前提。清理确实没有页面消费者的 UI 控件、接口和配置时，先用代码搜索和测试确认没有采集器或旧命令依赖，不能为减文件数破坏已验证链路。

## 组件与数据流

1. GitHub Actions 负责定时启动采集，运行仓库现有的 `python -m radar collect`，不是 Vercel、Dot、浏览器或用户电脑在后台常驻运行。
2. `sources` 模式按 GitHub、HF Models、HF Spaces 三个来源读取和校验数据，保存新词、来源证据、运行状态到 Neon。
3. `sites` 模式读取设置中已启用的竞品，安全获取完整 Sitemap，保存 URL 基线并计算后续新增/消失事件。第一次完整采集只建立基线，不产生“新增 139 页”之类的虚假变化。
4. Vercel 上的现有网站从 Neon 读取总览、新词、竞品和设置状态；设置页只允许修改竞品配置，不提供手动抓取、删除历史或直接改关键词的操作。

左侧只保留“总览 / 关键词看板 / 设置”；关键词看板右侧顶部只有“新词 / 竞品”。总览默认今天（北京时间）且可切换日期；新词页显示当天的更新总览与逐条线索（名称、来源、发现时间、现有操作）；竞品页按站点查看 Sitemap 新增/消失页面；来源基线和竞品输入放设置页。已确认的分页保留，以免多站点、多页面时整页失控。

## 定时规则与容量

沿用 `.github/workflows/free-platform.yml` 的免费采集工作流：GitHub/HF 在 UTC 00:00、08:00、16:00 触发（北京时间 08:00、16:00、次日 00:00）；竞品在 UTC 01:30 触发（北京时间 09:30）。这是计划触发时间，GitHub Actions 可能延迟启动，不承诺精确到分钟。站点模式单次最多处理 20 个任务，超过的站点不得被展示成“当天无变化”，而应显示未采集或待处理；这个版本不保证超过 20 个站点都能每日覆盖。

GitHub Actions 不要求仓库公开：当前 `mingjobo/new-term-radar` 确实是公开仓库，但将来改成私有也可继续运行；私有仓库的运行分钟数按 GitHub 当时的套餐额度计算。仓库可见性不是本次部署步骤，不为采集而修改。

正式运行只在受信任的 `main` 分支、生产 Neon 凭据配置完成并通过生产验收后开启 `FREE_RADAR_ENABLED`。原有付费/旧流程的 `RADAR_ENABLED` 保持关闭。开发分支和正式站使用各自数据库环境，不能把开发数据写进正式库。定时任务的数据库连接只放 GitHub Actions 服务端密钥中；Vercel 不持有采集器写入密钥。

## 失败与公开编辑边界

- 来源采集失败或覆盖不足时，不推进来源基线，不把未采集写成零新词；保留可见的失败/不完整状态，下一个定时窗口再尝试。
- Sitemap 失败、缺页或被截断时，不更新 URL 基线，也不报页面消失；同一站点同一北京时间日期的成功采集保持幂等。暂停站点保留历史、停止后续采集。
- 设置接口继续拒绝私网/本机地址、带凭据或非标准端口的网址，限定 Sitemap 与主页同主机，限制请求体大小，拒绝重复站点；保留同源浏览器请求检查。但同源检查不是“只有我能改”的身份验证，能直接调用公开接口的人仍可尝试改设置。
- 公开可编辑与自动采集同时存在，外部人员可能恶意添加站点或消耗额度。第一阶段依靠网址校验、单次 20 站点、任务 25 分钟超时及 Neon/GitHub 使用量观察控制影响；若实际出现滥用，再单独讨论是否增加限制，不暗中加入登录或口令。

## 部署顺序与验收

1. 在当前开发分支完成免登录和精简改动，先跑相关单元、集成和真实浏览器测试；确认无认证信息也能打开页面和设置，非法输入不能写入。
2. 核对 Neon 正式库现有 `radar_*` 表与旧 Trends 表；只补齐采集和网页需要的服务端数据库权限，不重建/清空现有数据。网页和 GitHub Actions 分别设置各自生产密钥，浏览器不接触密钥。
3. 把已验证版本更新到 `main`，由现有 Vercel 项目发布正式网站。用未登录浏览器验收总览、新词、竞品、公开设置修改；确认首个真实竞品快照只有基线、无虚假变更。
4. 在受信任的正式环境先做一次人工触发验收，确认 GitHub/HF 和竞品数据实际进入生产 Neon，失败能被看见；然后开启 `FREE_RADAR_ENABLED`，观察至少一轮来源定时运行和一轮竞品定时运行的 GitHub Actions 记录与网页结果。不能把“工作流文件存在”当成“定时采集已运行”。
5. 回滚先关闭 `FREE_RADAR_ENABLED`，再回退网页版本；保留 Neon 数据以供排查。旧 Trends 表不改动。

完成标准：正式网站免登录可用；设置能公开添加/暂停/恢复竞品；GitHub/HF 定时产生真实新词线索；竞品定时采集在第一次完整快照后、后续实际变化时只报告 Sitemap 新增或消失的 URL；失败和超过本版容量时不会报假零或假删除；工作流和网页均有实际生产验收记录。
