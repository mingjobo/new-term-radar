# 免费关键词研究工作台 V1：多站点页面增减监测需求

日期：2026-10-21
状态：待用户评审
适用仓库：`mingjobo/new-term-radar`
参考：[原免费平台设计](2026-10-15-free-keyword-platform-design.md)

## 1. 背景与目标

现有开发分支已验证 GitHub、Hugging Face → Neon → 只读网页的首次链路，但自动重复采集尚未启用。现有网页展示新词及来源状态，没有竞品网站的页面增减清单。

本版扩展**现有的 Term Signal 关键词研究网站**，不是另建一个竞品监测网站。保留首页的 GitHub/Hugging Face 新词列表、三张来源状态卡和新词研究卡，在同一导航和视觉体系中加入多个竞品网站**哪些网址新进入、哪些网址移出站点地图**的概览与详情。首个试点网站是 [aiphotoeditor.com](https://aiphotoeditor.com/)；2026-10-21 读取其 [robots.txt](https://aiphotoeditor.com/robots.txt) 可找到 [Sitemap](https://aiphotoeditor.com/sitemap.xml)，当时 Sitemap 列出 139 个网址。这个数字是现场观察，不是写死的产品目标。

“移出”在 V1 中只有一个含义：某网址存在于该站点上一次完整的 Sitemap 快照，却不在本次完整快照中。系统不据此声称网页已删除或返回 404。首次采集只建基线，不产生新增或移出事件。

## 2. 用户与成功标准

用户是个人研究者，需要在**同一个网站**里先看 GitHub/HF 新发现了什么名字，再看哪些竞品站点有新页面或页面移出。站点和页面数量可能很多，因此首页只给竞品动态摘要，站点页先汇总网站，不平铺所有页面事件。

V1 完成时，用户应能在工作台回答：

1. 今天哪些站点有新增或移出的网址，各有多少？
2. 点进一个站点后，具体是哪些网址，系统何时发现，原始链接在哪里？
3. 某站点本次是否采集成功，结果是正常无变化、首次建档、失败，还是数据不完整？
4. GitHub/HF 的新词采集是否按计划自动更新？
5. 在同一个工作台里，能否从新词线索、来源状态切换到竞品页面，并返回原有的新词研究卡？

## 3. 范围与交付顺序

| 阶段 | V1 交付 | 可验收结果 |
|---|---|---|
| A. 跑活现有来源 | GitHub、HF Models、HF Spaces 完成第二次实际采集，再接入每 8 小时自动运行 | 运行记录和网页时间更新；同一周期重跑不重复生词 |
| B. 多站点 Sitemap 监测 | 可配置多个站点；每日读取各站完整 Sitemap；逐站保存基线并计算新增/移出 URL | 首次运行零事件；下一次完整运行产生准确差分；单站失败不影响其他站 |
| C. 工作台融合展示 | 保留现有新词首页和研究卡；增加统一导航、竞品概览、站点汇总及单站 URL 清单 | GitHub/HF 的现有查看路径仍能使用；大量竞品事件可搜索、筛选和分页 |
| D. 预览验收 | 在开发 Neon 分支及 Vercel 预览站点验证真实链路 | 页面计数与数据库记录一致；失败/不完整时无虚假移出 |

本需求覆盖并收窄原设计中 Sitemap 与工作台的 V1 范围。V1 先交付 URL 名单变化；原设计中的页面文字抓取、用途词推断、3/14 天复查及日报周报不属于本次验收。

## 4. 用户故事与验收条件

### US-001：配置多个监测站点

作为研究者，我希望系统按一份站点清单逐站监测，以便从 aiphotoeditor.com 扩展到更多竞品。

- [ ] 站点清单可配置站点名称、主页地址及可选的 Sitemap 地址；未指定 Sitemap 时先按该站 `robots.txt` 声明发现。
- [ ] 各站点独立建立快照和显示状态；新增站点不会重置已有站点的历史。
- [ ] 没有可用 Sitemap 的站点明确显示“无法监测”，不回退为全站爬取。

### US-002：首次建档

作为研究者，我希望首次采集只记录当前网址，以免把存量页面误认为今天新增。

- [ ] 首次完整读取一个站点时保存 URL 名单、采集时间和网址总数。
- [ ] 此次新增数和移出数都为 0，状态为“基线已建立，等待下次比较”。
- [ ] 首次读取为空、失败、超出预算或只完成部分 Sitemap 时，不建立基线。

### US-003：识别新增和移出的网址

作为研究者，我希望看到两次完整采集之间的 URL 名单差异。

- [ ] 本次有、上次没有的 URL 记录为“新增页面”；上次有、本次没有的记录为“移出站点地图”。
- [ ] 每条事件保存站点、完整 URL、类型和**发现时间**；发现时间不标作网站实际发布时间。
- [ ] 同一采集周期重跑不产生重复事件；曾移出的 URL 后来重新出现，作为该次新增记录。
- [ ] 网址比较仅做保守规范化，避免主机名大小写、默认端口及片段标记产生假差异，不合并不同路径。

### US-004：异常时保护旧基线

作为研究者，我希望站点暂时不可访问时，工作台明确显示问题，而不是报告大量页面被移出。

- [ ] Sitemap 索引或任何必要分片读取失败、结果为空、格式异常或超过预算时，该站状态为失败或不完整，旧基线保持原样，新增/移出事件均不产生。
- [ ] 一个站点失败时，其他站点继续采集和提交。
- [ ] 每个站点显示最近一次成功时间与最近一次尝试状态；数据过期有明确提示。

### US-005：与现有关键词网站融合

作为研究者，我希望在现在查看 GitHub/HF 新词的同一个网站中发现竞品页面线索，不用切换到另一套网站。

- [ ] 现有首页 `/` 保留“今日新名称/今日证据/来源在线”、GitHub/HF 三张来源卡、新词列表及“研究卡”链接；接入竞品功能后，这些内容仍可正常读取。
- [ ] 共用现有 Term Signal 页头、字体、色彩和只读标识；页头或首页提供明确的“新词线索”“竞品页面”“来源状态”入口。新词线索和来源状态可定位到首页对应区域，不要求 V1 新建关键词列表页。
- [ ] 首页在来源卡之后、新词列表之前增加一块紧凑的竞品概览：今日新增 URL、今日移出 URL、异常站点数，以及最多 5 个有变化的站点和“查看所有站点”入口；不在首页铺开 URL 明细。
- [ ] 站点汇总页与单站详情沿用同一页头和导航；从竞品页可返回新词首页，现有 `/terms/{id}` 研究卡路径不改变。
- [ ] GitHub/HF 新词和 Sitemap URL 变化视觉上分区，计数各自独立；不把 URL 路径自动称为“关键词”，也不暗示两类线索存在关联。
- [ ] 在浏览器里从首页分别进入一张原有新词研究卡和一个竞品站点详情，再返回首页；桌面和窄屏均可完成。

### US-006：站点汇总页

作为研究者，我希望先看到站点级别的变化数量，以便在很多站点里找到最值得点开的站点。

- [ ] “竞品页面”默认显示按站点排列的列表，列出站点名、选定时间范围内新增数、移出数、最近成功时间和状态。
- [ ] 支持按站点名搜索、只看有变化站点、按状态筛选；默认按最近变化时间排序。
- [ ] 汇总页显示监测站点数、新增 URL 数、移出 URL 数和异常站点数；统计口径与列表一致。
- [ ] 站点很多时使用分页；浏览器实测窄屏仍可读，不把所有 URL 平铺在首页。

### US-007：单站页面清单

作为研究者，我希望点进一个站点后快速找到具体 URL。

- [ ] 单站页面提供“新增”“移出站点地图”“全部”切换、URL 路径搜索、时间范围筛选和分页；每页默认 50 条。
- [ ] 每行显示发现时间、类型、可读的 URL 路径和“打开原始页面”链接；可查看完整 URL。
- [ ] Sitemap 不保证提供页面标题，V1 以 URL 路径为主标签，不为填标题而逐页抓取正文。
- [ ] 首次建档、没有变化、采集失败和无匹配结果分别显示明确的空状态；使用浏览器验收这些状态。

### US-008：现有新词来源自动更新

作为研究者，我希望 GitHub/HF 数据自己更新，而不需要点击“研究”。

- [ ] GitHub、HF Models、HF Spaces 使用独立的免费任务每 8 小时运行；竞品 Sitemap 每日运行一次。
- [ ] 工作台的新词区域继续展示有来源的词条，来源状态显示最后成功时间、本次运行结果和本次新增数。
- [ ] 自动任务只使用平台写入凭据；网页继续使用数据库只读凭据。
- [ ] 免费任务不调用原上游工作流的付费 API；在预览环境先验证重复运行和故障状态。

## 5. 功能规则

- **FR-01：站点来源。** 每个站点有稳定的标识和单独的 Sitemap 快照。配置支持多个站点，首批只启用 aiphotoeditor.com 进行真实验收。
- **FR-02：发现方式。** 仅读取公开 Sitemap；可处理普通 Sitemap 和 Sitemap 索引及其必要分片。遵守 `robots.txt` 与站点的抓取间隔。
- **FR-03：完整性。** 仅在该站所有必要 Sitemap 成功、格式有效且未超预算时提交新快照。部分成功不能用于计算新增或移出。
- **FR-04：差分。** `新增 = 本次 URL 集合 − 上次成功 URL 集合`；`移出 = 上次成功 URL 集合 − 本次 URL 集合`。首次成功只有快照，没有事件。
- **FR-05：移出语义。** “移出”只表示不在 Sitemap；不检查目标页面的 HTTP 状态，也不标记“已下线”。
- **FR-06：时间。** 事件时间是系统发现时间。数据库存带时区的时间；界面“今天”和日期筛选按北京时间计算。
- **FR-07：隔离与去重。** 站点各自成功或失败；同一站点同一周期的同一 URL/类型最多记录一次。
- **FR-08：记录。** URL 快照、事件、运行状态持久保存在现有 Neon 平台。页面增减事件与关键词线索分开存放，不自动把 URL 路径当作有搜索需求的新词。
- **FR-09：站点汇总。** 先展示站点级计数和健康状态；具体 URL 只在单站清单出现。搜索、筛选和分页在服务器侧处理。
- **FR-10：页面链接。** 事件可回到原始 URL；移出事件的链接可能已不可访问，界面仍保留它作为原始证据。
- **FR-11：运行频率。** 现有 GitHub/HF 来源每 8 小时采集；Sitemap 站点每日采集。缺一次运行后只按真实最新时间重新读取，不编造错过时段的历史事件。
- **FR-12：只读网页。** 网页只查询已保存结果，没有抓取按钮或写库权限；页面文本安全呈现，外部链接仅允许 HTTP(S)。
- **FR-13：统一信息架构。** 首页 `/` 继续承担新词概览与列表，`/terms/{id}` 保持原有研究卡；竞品站点汇总与单站清单作为同站点的新视图，统一导航和返回路径，不另起网站或第二套页面外壳。
- **FR-14：概览与来源状态。** 首页只显示竞品计数及最多 5 个站点摘要；GitHub/HF 三张来源卡保持可见。竞品采集健康状态只需首页总体提示，逐站状态放在站点汇总/详情，避免每个竞品都占一张来源卡。

## 7. 技术约束与现有项目衔接

- 复用已有 Python 采集入口、请求预算、Neon 读写角色、运行记录和 Vercel 只读展示；网页沿用 `radar_platform/templates/index.html`、`radar_platform/static/app.js`、`app.css` 的现有外壳和阅读方式。竞品事件需要独立的持久记录；不要塞进 `radar_terms` 冒充关键词。
- 站点清单 V1 由仓库配置维护，支持一次配置多个站点；不增加网页上的站点编辑功能或多用户管理。
- 沿用原设计的单站安全上限：最多读取 20 个 Sitemap 文档、20,000 个 URL；超限标记不完整并保留旧快照。实际默认值及大站点行为须在实施计划中写出测试。
- 2026-10-21 所见 aiphotoeditor.com Sitemap 的 `lastmod` 值相同，因此 V1 不使用 `lastmod` 判断页面是否变化；只比较 URL 集合。
- 预览阶段先使用现有 Neon `dev-free-platform` 分支和 Vercel 预览部署。正式启用前验证采集凭据与网页只读凭据隔离。

## 8. 非目标

- 不比较已有页面的标题、正文、价格、图片或截图；不生成“变化前/变化后”内容对比。
- 不检查移出 URL 的 404/410，不推断实际下线时间。
- 不推断搜索量、SEO 难度或商业价值；不自动把页面路径转成关键词。
- 不抓取没有 Sitemap 的整站，也不登录竞品后台。
- 不做站点自助添加、通知推送、付费 API、3/14 天复查、日报周报或 GSC 集成。

## 9. 验收与成功指标

1. **真实建档：** aiphotoeditor.com 首次完整采集成功，保存当次实际 URL 数；新增和移出均为 0。重复执行同一周期没有事件。
2. **受控差分：** 测试快照中加入 3 个 URL、移去 2 个 URL，恰好得到 3 条新增、2 条移出；第三次同样快照得到 0 条。
3. **故障保护：** 分片缺失、空内容或预算耗尽时，旧快照版本和事件数不变；其他站点仍可成功。
4. **多站点可读：** 用至少 20 个站点、单站至少 1,000 条示例事件验收汇总、搜索和每页 50 条分页；汇总数与详情数一致。
5. **自动运行：** GitHub/HF 连续两次定时运行有真实记录；竞品站点连续两次每日运行有真实记录。站点无变化时显示 0，不伪造事件。
6. **预览网页：** 浏览器中可从站点汇总进入单站清单，再打开原始 URL；错误状态和首次建档文案均正确，网页账号没有数据库写权限。
7. **融合回归：** 同一个预览网站的首页仍能显示 GitHub/HF 来源卡、新词列表和研究卡；首页可进入竞品站点汇总/详情并返回；两类计数不互相混算，桌面与窄屏均通过浏览器验收。

## 10. 已定决策与待评审点

- 已定：V1 只监测 URL 名单新增与移出；移出以完整 Sitemap 差分为准。
- 已定：多站点先看站点汇总，点进站点再看可筛选、可分页的 URL 清单。
- 已定：aiphotoeditor.com 是首个真实试点；图中的事件数不是现场结果。
- 已定：V1 的页面数据不自动转成关键词；GitHub/HF 新词作为工作台另一部分持续自动采集。
- 已定：竞品监测融合进现有 Term Signal 网站；保留原有 GitHub/HF 首页和研究卡，新增同站点竞品视图，不另起独立网站。

本文档用于评审需求和验收口径；用户确认后再拆分实施任务，不在本次需求文档工作中修改采集程序或网页。
